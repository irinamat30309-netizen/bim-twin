# GEOREF-RTK-HOWTO — как закрыть привязку объекта сканом с RTK (вариант A)

Короткая инструкция для заказчика/оператора сканера и для инженера BIM Twin. Цель — за один
скан с RTK получить облако в реальных координатах и автоматически геопривязать модель
(IFC), закрыв позиционную привязку (сейчас UNVERIFIED: у сентябрьских сканов нет ни GNSS,
ни контрольных точек с внешними координатами).

---

## 1. Что нужно заказчику/оператору на объекте

1. **Включить RTK на Lixel L2Pro** и убедиться, что есть **RTK-фикс**:
   - поправки: NTRIP (SIM-карта/интернет на сканере) **или** локальная база;
   - в статусе Lixel должен гореть **RTK Fixed** (не Float, не Single).
   - `RTKStatus=true` в проекте; в `project_data/gnss.csv` должны появиться строки.
2. **Система координат и высоты — согласовать ДО скана:**
   - по умолчанию — **WGS84 / UTM (EPSG:32xxx)**; для Киева (30.5° в.д.) — **UTM зона 36N,
     EPSG:32636** (WGS84) или **EPSG:25836** (ETRS89). Внимание: **EPSG:25833 — это зона 33N
     (центральный меридиан 15° в.д.), для Киева не подходит**; если у заказчика есть основания
     использовать именно её — сообщите заранее (инструмент будет работать, но с предупреждением);
   - если нужна **УСК-Київ (местная)** — дайте параметры перехода УСК↔WGS84 (или однозначные
     координаты 3–4 точек УСК), либо заранее договоритесь, что привязка делается в UTM;
   - **высоты**: уточнить — эллипсоидальные (по умолчанию) или ортометрические (тогда
     инструмент прибавит `undulation`, если она есть в `gnss.csv`). Высотная система —
     Балтийская или местная (для модели это неважно, важна фиксация в отчёте).
3. **Минимум 3–5 RTK-фиксов вдоль маршрута** (лучше — весь маршрут с частотой 1–10 Гц):
   - фиксы должны покрывать **весь маршрут** (начало/середина/конец), а не только старт;
   - нельзя делать съёмку «вслепую»: если фикс пропал в середине маршрута, эти участки
     инструмент не использует (видно по `fix rows / сопоставлено`).
4. **Длина маршрута и геометрия**: инструмент подбирает поворот+масштаб+сдвиг по фиксам;
   чем длиннее маршрут и чем больше он «раскрыт» (не только прямая), тем точнее поворот.
   Для объектов 30–100 м достаточно 5–10 фиксов, разнесённых на 10–50 м.
5. **Проверить, что данные записались (перед уходом с объекта):**
   - `project_data/gnss.csv` — **не 0 байт и не только заголовок**: открыть текстовым
     редактором, убедиться, что есть строки с `status` = fix/3–5 и непустыми `latitude`,
     `longitude`, `altitude`;
   - `project_data/poses.csv` — 30–60 строк/с, координаты меняются;
   - в `log/project.json`: `"RTKStatus": true`, `DataMonitor.gnss_detect.frames > 0`;
   - в Lixel Studio — статус RTK Fixed при съёмке.
6. **Что прислать** (папка проекта Lixel целиком):
   ```
   project_data/
     gnss.csv          ← заполненный: timestamp,status,latitude,longitude,altitude,...
     poses.csv         ← timestamp,x,y,z,qx,qy,qz,qw
     log/project.json  ← должен содержать RTKStatus=true
     model/…           ← octree/облако
   *.xbin (или map.las) ← облако проекта
   ```
   Достаточно `.zip` папки проекта Lixel. **Не пересжимать облако в сторонних программах** —
   нужны исходные `gnss.csv`/`poses.csv`.

## 2. Что делает инженер BIM Twin после получения скана (автоматически)

Одна команда (при необходимости — вторая для IFC):

```bash
python tools/scan2bim-py/georef-rtk.py --project "D:\scan\ln_amosova_rtk_2026-XX-XX" \
       --out georef.json --strict
```

Результат `georef.json` содержит:
- `crs`: EPSG, зона, WKT (`IfcProjectedCRS`);
- `transform`: поворот, масштаб, сдвиг (E0/N0/H0), готовый `ifc_map_conversion`;
- `fix`: сколько GNSS-строк, сколько fix, сколько сопоставлено с позами, **невязки
  rms/max** по точкам (порог `--strict`: 0.15 м);
- `cloud_bbox_utm`: габарит облака в реальных координатах;
- `transform.ifc_check`: проверка, что формула IfcMapConversion воспроизводит точки (<5 мм);
- `warnings`: предупреждения (не та зона, WGS84↔ETRS89, LAS не найден и т.п.).

Если RTK-проект содержит облако/модель в кадре Lixel (x,y — план, z — вверх) — привязка
применяется напрямую. Если модель построена нашим конвейером (`las-to-bin.js` → y-up, с
`origin = ox,oy,oz` из его JSON-меты), то дополнительно:

```bash
python tools/scan2bim-py/georef-rtk.py --project "…" --out georef.json --strict \
       --local-plan xz --from-las-origin ox,oy,oz
```

Во втором случае инструмент пересчитывает позы в кадр скана, подбирает трансформацию и
выдаёт `ifc_map_conversion` с `source_transform` (план зеркалится как в `las-to-bin.js`).

Геопривязанный IFC (реальный `IfcMapConversion` вместо прежнего `[500000,6000000,120]`):

```bash
node tools/scan2bim-py/json-to-ifc.js py2-final-v5.json py2-final-v5-georef.ifc \
     --georef-file georef.json
python tools/scan2bim-py/validate-ifc.py py2-final-v5-georef.ifc --json validate.json
```

`validate-ifc.py` должен дать **ERROR=0, WARNING=0, арность=OK** (проверено на синтетике:
`georef-rtk-test.py` → PASS).

## 3. Проверка после получения данных: «данные появились»

Быстрая проверка (Linux/WSL/PowerShell — любое):

```bash
python - <<'PY'
import csv
rows = [r for r in open(r'project_data/gnss.csv', encoding='utf-8') if r.strip() and not r.startswith('#')]
print('строк gnss:', len(rows))
print('первая:', rows[0].strip() if rows else '—')
fix = [r for r in rows if 'fix' in r.lower() or r.split(',')[1].strip() in ('3','4','5')]
print('fix:', len(fix))
PY
```

Или сразу прогнать инструмент: если он возвращает код **2** и сообщение
«нет данных fix: в gnss.csv N строк, но ни одна не RTK fix» — данных нет, скан нужно
повторить. Код **0** — привязка получена (смотреть невязки в georef.json).

## 4. Частые проблемы и что делать

| Симптом | Причина | Решение |
|---|---|---|
| gnss.csv только заголовок, `RTKStatus=false` | RTK не работал (нет поправок/сети) | включить NTRIP/базу, проверить статус RTK Fixed на сканере до съёмки |
| `status` = 2 (RTK float) везде | поправки есть, но не «фикс» | дождаться RTK Fixed (обычно 10–60 с), инструмент float не принимает (можно явно `--accept-status "2,fix"`, но невязка будет хуже) |
| фиксы есть только на старте | RTK потерял фикс в помещении | снимать маршрут у окон/входов или использовать базу ближе; минимально нужно 3 разнесённых фикса |
| невязка > 0.15 м | плохая геометрия маршрута (все фиксы в линию/кучно), проскальзывание SLAM | длиннее маршрут, больше разнесённых фиксов, повторить скан |
| инструмент пишет «EPSG:25833 — зона 33N…» | заказали 25833, а объект на 30.5° в.д. | использовать EPSG:32636/25836 (зона 36N) |
| `IfcMapConversion` в IFC не изменился | старый `--georef` без `--georef-file` | использовать `--georef-file georef.json` |

---

## 5. Критерий «привязка закрыта»

- `georef-rtk.py --strict` вернул **exit 0**;
- в `georef.json`: `ok: true`, `accuracy.max_m ≤ 0.15 м` на **≥3** точках;
- `rms ≤ 0.05 м` (обычная точность RTK-фикса 2–3 см);
- IFC: `validate-ifc.py` — 0 ERROR; `IfcMapConversion` содержит реальные E0/N0/H0/поворот/scale;
- после этого позиционная привязка модели к координатам проекта считается подтверждённой
  (при необходимости — доп. сверка с осями 7 200 через `georef.json` + план).

Инструменты: `tools/scan2bim-py/georef-rtk.py`, `georef-rtk-test.py` (синтетика),
`json-to-ifc.js --georef-file`, `validate-ifc.py`.
