# COLOR-REPAIR-r181 — «нажал Раскрасить по фото — облако осталось серым»

Итог: причина найдена и исправлена. Файл раскраски **создавался корректно** (в нашем E2E сразу после кнопки в файле
95–96 % точек с цветом, std RGB 13.8–14.3), но приложение **не показывало результат**: после завершения оно
открывало новый LAS через диалог предпросмотра/импорта («Загрузить N млн»), и до подтверждения на экране оставалось
старое серое облако. Плюс в приложении пост-обработка (fill+denoise) шла в main-процессе: на 600+ млн точек окно
зависало на десятки минут, а неисправленная оценка места могла уронить операцию в конце. Всё три места исправлены и
проверены в реальном Electron (CDP) на реальном .xbin.

## 1. Воспроизведение (реальный Electron, CDP, без playwright)

Запуск настоящего приложения: `electron . --remote-debugging-port=9333 --user-data-dir=<scratch>\userdata`,
управление через CDP (Node 24 global `WebSocket`, скрипт `_scratch/r181/cdp.js`): клики по `#modelInput`,
диалогам импорта, кнопке `#cpPhotoColor`; проверки — DOM панели «Свойства облака», буферы вьюера, файлы.

Тестовые серые облака (собраны нашим же `xbin-lidar` из того же `.xbin`):

* `D:\Skan\port\fasadamosova\test-gray-36m.las` — 35 952 837 точек, окно 120 с полной плотности (xbin 22 ГБ);
* `D:\BIM-TWIN-TEST\r55\detail-r172\sub-130m.las` — 130 000 000 точек (непрерывный кусок полного фасада
  `facade-detail-edgeoff.las`, 671.8 млн), рядом положены hardlink `.xbin` и `project_data\poses.csv` — как у заказчика.

Сценарий заказчика воспроизвёлся 1-в-1: после открытия серого LAS панель писала
«Цвета в файле нет: RGB — серая яркость отражения лидара…» с кнопкой «Раскрасить по фото камер».
После кнопки + подтверждения:

* файл `*-color.las` создавался и был **цветным** (95.09 % точек с отличным от серого RGB на 36-M облаке);
* но вьюер продолжал показывать **старое серое** облако, панель не менялась — пока вручную не подтвердить
  диалог импорта нового файла. Именно это видел заказчик (скрин панели с серой нотой).

## 2. Причины (три)

1. **UI не открывал результат** (`renderer/app.js`, успешная ветка `__bimPhotoColor`):
   `return window.__bimOpenCloudPath(r.path, { fresh: true })` — без `skipPreview`, поэтому для LAS открывался
   диалог «Импорт/предпросмотр: Загрузить N млн» и ждал подтверждения. Старое облако оставалось на экране,
   пользователь видел «ничего не произошло». Файл при этом уже был цветным.
2. **Пост-обработка в main-процессе** (`main.js`, `photoColorAuto`): после параллельной раскраски тайлов вызывался
   `postColor()` (fill + денойз по всему LAS) синхронно в main-процессе. На 36-M это ~1–2 мин, на 637 M —
   десятки минут «не отвечает»; прогресс замирал, автопереключение на результат не наступало. В CLI путь уже был
   параллельным (`postParallel` на worker_threads), в приложении — нет.
3. **Недооценка свободного места** (`photoColorNeed`): параллельный путь держит на диске тайлы + склейку + пост
   (~2× исходника), а проверялось ~1.05×+0.62×. На больших сканах это могло дать ENOSPC в конце (после долгого
   ожидания) — ещё один сценарий «осталось серым».

## 3. Что исправлено

* `renderer/app.js`: результат открывается сразу, без диалога:
  `__bimOpenCloudPath(r.path, { fresh: true, skipPreview: true, noAllAsk: true })`.
* `main.js` (`photoColorAuto`): пост-обработка теперь `recolor-post.postParallel` в `worker_threads`
  (по тем же диапазонам строк, что и тайлы, с прогрессом 87→98 % в UI); main-процесс не блокируется.
* `main.js` (`photoColorNeed`): `2.25 × размер исходника + 2 байта/точку` — оценка пика параллельного пути;
  при нехватке места операция сразу отказывается с понятным сообщением, а не падает в конце.
* `main.js` (`bim:photoColorCloud`): `photo.colored` ограничен числом точек (раньше из-за перекрытия кусков
  в прогрессе могло показывать >100 %).
* `recolor-post.js`: `postParallel` принимает `onProgress` (по завершении каждого куска) — UI-прогресс живой.
* Новый тест `test/r181-color-repair.test.js` (3 теста): автопереключение с `skipPreview`; пост через
  `postParallel`, а не `postColor` в main; оценка места >2× исходника.
* `MANIFEST.sha256` перегенерирован (`node scripts/release-manifest.cjs`, 888 файлов, verify OK).

## 5. Для заказчика (637 M / 22 ГБ .xbin)

* Нажать «Раскрасить по фото камер» ещё раз: результат сам откроется цветным, без диалога.
* Время на 8–16 потоках ~17–21 мин (r180: параллельные тайлы + `frameStride=2`; r181 убрал однопоточный пост
  и зависание UI). Прогресс в окне обновляется и на этапе заполнения/денойза.
* Нужно свободно ~50 ГБ на диске вывода (2.25× исходника); при нехватке — сразу понятная ошибка.
